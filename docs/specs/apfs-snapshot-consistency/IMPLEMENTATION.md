# Implementation

- The observed session-owned SettingsStore retains accepted maintenance operation IDs while Settings observes daemon terminal states; AppModel remains a non-observable coordinator. It renders active/paused observation, permits resuming the same operation, and no longer fails a running operation after 60 polls. Snapshot status uses a generation fence, a pane-scoped five-second read-only refresh task, last-successful-check timestamps and a separate refresh error. Deterministic callback-order tests exercise a late 72-blocker reply after a verified zero reply; the regression script removes the production fence to prove red before running the candidate green. Store publication tests verify that suspend/resume and terminal transitions notify consumers immediately. Manual and automatic status queries preserve installation and terminal-operation errors. No root-helper, Access, protocol or durable state changes are involved. Synthetic previews include processing, paused observation and the zero-blocker ready state.

- The CLI permits a stale compatible helper with an exact distinct released-only inventory-drift partition to use the existing guarded replacement transaction. Replacement preserves journal records and rechecks Access idle and status under locks; only the verified replacement can reconcile them. Rust negatives cover mixed partitions, duplicate/invalid IDs, missing fields, matching build identity, and an incorrect candidate-state token; the positive fixture uses the production `released_inventory_drift` token. The hosted ambiguous-manifest negatives explicitly seed incomplete released tombstones so their unknown classification matches the exercised terminal state. The hosted installer fixture verifies the published rc.142 Access 0.2.1 artifact against the trusted component lock, reproduces 72 drift rows, verifies replacement identity and journal preservation, then exercises journal-bound Release to reconcile them to zero. Settings offers Update first in this state and suppresses the duplicate wait/reconcile prompts.

- Release checks the authenticated caller against the stored journal owner before age-gated
  recovery or any journal mutation. The stale empty-reservation regression proves a foreign
  caller cannot change the row or invoke inventory/deletion, while its owner retains the
  conservative cleanup path when the baseline is invalid.

- Historical caller-owned `snapshot-access/mounts/<uid>/<lease>` paths use a separate
  journal-only retirement branch for stale released rows whose recorded snapshots are already
  absent. A fixed system observer queries volume identity, APFS inventory, no-follow metadata
  and the kernel mount table. Deterministic tests inject observations at the same repair/status
  boundary; production has no command-replacement or runtime fixture hook. The compare-and-swap
  preserves unrecorded inventory and refuses concurrent volume owners. An explicitly ignored
  administrator-authorized diagnostic opens the installed journal read-only and exercises the
  same verification predicates without executing an UPDATE. It is not run by ordinary CI.

- Installer startup polling uses a monotonic 20-second window with 250ms sleeps clamped to the remaining time. Immediate connection refusal no longer consumes a fixed four-probe budget, slow calls consume the same clock, and a late ready reply is rejected. Existing component/build and installed-file hash checks remain mandatory. Deterministic clock tests and a hosted mutation of the old four-probe loop cover the regression; the macOS installer fixture can hold a disposable SQLite journal lock to delay the real helper.
- Snapshot failure classification retains the fixed `mount_permission_denied` reason when sanitized diagnostics identify the mount phase and `mount_apfs` permission denial. This distinguishes mounting from generic source access without forwarding paths or arbitrary command output to the UI.

- `crates/snapshot-helper`: user-session Snapshot Access protocol and journal-backed lifecycle,
  including recorded mount-device identities, migratable lease journals, reservation renewal while
  snapshot creation is in flight, unique firmlink resolution, and descriptor-relative no-follow
  reads. Missing or changed mount identities fail the current strict run before source bytes are
  served.
- `crates/snapshot-helper/src/mount_helper.rs` and `src/bin/televybackup-snapshot-mount-helper.rs`:
  root IPC, peer-UID source-path authorization, serialized helper-owned snapshot creation through `RecordCleanup`, UUID journal, crash recovery, and component version `0.5.7` validation that
  binds the requested snapshot name to its manifest UUID before `mount_apfs`, passes the validated
  `/dev/<device>` identity instead of a mutable request pathname, and verifies the mounted device
  afterward. Source-path authorization runs in an exec'd one-shot helper before the server runtime
  starts, and released leases remain as auditable tombstones; a later reserve audits their
  validated baseline and re-blocks the volume if inventory changed. Deletion clears only the
  successfully consumed manifest entries, retains the original reservation baseline, and only
  releases after the post-deletion inventory returns to that baseline; migrated rows without a
  validated baseline remain blocked. A stale row with a mounted root is recoverable only when its
  recorded mount-device identity is present and positive; missing identity remains an unknown
  blocker and ordinary cleanup refuses to unmount the path. The explicit legacy-repair operation
  may backfill that identity only for an age-gated row whose managed root is absent and whose UID,
  volume/device binding, reservation manifest and snapshot inventory all validate, then reuses journal-bound
  `Release`; rows that fail any check remain untouched and blocking. If snapshot deletion succeeds before a process
  crash, an exact reservation-baseline retry records the released tombstone idempotently. The
  installed `0.9.8` helper remains
  migration-readable only.

- `crates/cli/src/snapshot_mount_service.rs`: explicit administrator-authorized mount-helper
  LaunchDaemon installation and status contract. Installation acknowledges success only after a bounded IPC probe confirms the current mount-helper component, protocol and candidate source commit, and the installed binary SHA-256 matches the candidate. The v4 wire `helper_version` remains `0.5.0` for the byte-identical approved Access artifact; additive `component_version` identifies the `0.5.7` implementation. Legacy Status without the additive identity fields remains readable but cannot acknowledge a new installation; a known legacy wire version (`0.5.0` or `0.9.8`) may authorize the guarded replacement path even when its positive `active_mounts` aggregate already includes a build identity, provided all additive classification fields are absent and Snapshot Access proves idle. The previous `0.5.5`, `0.5.4`, `0.5.3`, `0.5.2` and `0.5.1` components may also authorize that guarded replacement under their existing complete-classification predicates; the current `0.5.7` component may use the same guarded replacement when its build identity is stale and it reports the live, pending, recoverable and unknown partitions but omits only the newer inventory-drift field, or when every pending row has an exact candidate and no live, recoverable or unknown row remains. The candidate helper must classify inherited rows before readiness. The explicit `snapshot.mount_helper.repair_legacy` operation handles legacy identity migration; ordinary `Release` separately handles a validated unmounted prepared row whose device was never captured; it resolves stale device nodes through the journaled volume UUID, partitions manifests by snapshot UUID, and may clear an empty legacy reservation without deleting unrecorded snapshots. Refresh remains read-only. Unknown versions, current-helper status with a matching build but missing classification, active mounts that have not been safely handed to the candidate, and incomplete candidate partitions remain blocked. An installed helper whose mount state cannot be probed is rejected fail-closed; recovery bootstrap is allowed only when `launchctl` explicitly reports the service absent and the root-owned plist is present. Installer and helper mutating IPC share a root-owned file lock through the busy check, asset replacement and old-service bootout; recovery bootstrap releases and reacquires that lock before the final busy check, and replacement releases it before bootstrap so the new helper can acquire it during startup recovery.

- Snapshot Access persists a `cleanup_pending` lease when root-helper release is unavailable, retries that durable cleanup in the background and during status probes, and accepts an idempotent release retry for the recorded lease. The CLI and daemon expose an explicit cleanup-retry operation that waits for Snapshot Access to become idle, verifies the complete pending-plus-released-drift classification, and then reuses the journal-bound `Release` path; a malformed or racing inventory remains `snapshot_mount_helper.pending_cleanup` and fail-closed. The daemon also retries transient release transport failures, so a helper restart does not strand an active mount row until the next process restart.
- `macos/TelevyBackupApp/SnapshotMountHelperInstallation.swift`: coordinates administrator installation, renewed user-level Access registration, and the subsequent Access status check; preserves installation and registration errors across refresh, and rejects an exit-zero installation whose communication check still fails.
- `crates/daemon/src/control_ipc.rs` queries root Status independently of the approved Access artifact and exposes reachability, candidate readiness and build identities separately. `SnapshotMountHelperReadiness.swift` also binds readiness to the current app bundle, conservatively accepts legacy JSON as update-required, and supplies the production Settings update action. Final installation confirmation uses this same predicate. Status refresh remains read-only; cleanup retry is a separate serialized IPC operation.
- Root Status classifies live, pending-cleanup, recoverable-stale, inventory-drift, and unknown journal rows with additive optional fields. Missing additive fields remain unknown rather than zero for status, readiness, and reconciliation; known active and mixed test fixtures explicitly set every known category to zero when absent so they do not accidentally exercise the legacy-unknown path. The daemon exposes serialized `snapshot.mount_helper.reconcile`, `snapshot.mount_helper.retry_cleanup`, `snapshot.mount_helper.reconcile_inventory`, and `snapshot.mount_helper.repair_legacy` operations. Stale reconciliation requires the current helper component and build identity; cleanup retry accepts only the current or immediately previous cleanup-capable component, with the v4 wire identity and complete pending-plus-released-drift classification still required; inventory reconciliation accepts only exact released tombstones whose device/volume identity and changed baseline are verified. Legacy repair checks Snapshot Access idle, verifies the complete additive partition, and delegates age-gated candidate validation and journal-bound Release to the root helper. Each mutating operation queries the authenticated UID's complete helper Status, applies the same validation helper before and after releasing, and returns counts only. Ordinary Snapshot Access release never re-baselines a released row, and unknown states or malformed released tombstones remain untouched and reservation-blocking. Reconciliation writes the new inventory baseline and its confirmation in one SQLite transaction, so a failed post-update inventory check rolls the row back and leaves the drift blocker intact. Status requests serialize behind the helper's bounded status lock, and volume-inventory commands have a bounded child-process timeout. The Unix CLI delegates cleanup retry, inventory reconciliation and legacy repair to daemon operations so they share the maintenance lock with backup acquisition; the legacy previous helper remains eligible for a guarded update when it reports pending-only status without the newer optional inventory-drift field. Pending-cleanup, live, unknown, legacy, inconsistent, or identity-mismatched rows keep stale reconciliation blocked; inventory drift is reconciled after pending cleanup reaches zero; inventory reconciliation and legacy repair never open source files. Settings exposes each action only for its verified classification, waits for the operation's terminal state with a bounded polling deadline before refreshing, while an unreachable helper retains an install action.
- `SnapshotMountHelperStatusView.swift` is shared by Settings and the GitHub-hosted synthetic renderer. This is a deterministic readiness regression, not a full backup acceptance.

## Denied mount cleanup

`cleanup_mount` and journal-bound `Release` share a zero-device prepared-row cleanup path. The
private compile-time `CleanupObservation` seam substitutes only system observations and snapshot
commands in deterministic tests; production always uses fixed kernel, filesystem and diskutil calls.
There is no runtime replacement hook. Tests reproduce one failed mount plus 65 released tombstones,
then exercise immediate cleanup and the authorized Release retry, asserting original inventory and
zero source-volume blockers. Mounted roots, proof races, inventory drift, invalid identities,
foreign owners and denied deletion remain blocked. This proves the synthetic cleanup chain, not
installed FDA readiness or a completed user backup. Protocol v4, journal schema and approved Access
artifact remain unchanged; the root implementation component is `0.5.7`.

Status classification accounts for a changed inventory only when exactly one unfinished row on
the volume, owned by the same UID, records the exact extra UUID set and the same original baseline.
That owner remains blocking and must be released; unknown states, other owners, ambiguous rows and
unrecorded snapshots still report drift. This preserves the CLI/daemon pending-only retry contract
without weakening their safety gates. The ignored read-only failed-mount audit validates this
classification and the production kernel/volume absence predicates against an explicitly authorized
installed journal; it performs no cleanup and does not prove effective FDA or backup completion.

### Preparation deadlines and cleanup metadata

Acquire performs filesystem queries, snapshot creation and mounting, so it must not share the 30-second status deadline. The daemon uses a bounded acquisition deadline and keeps the maintenance lock through inventory-only reconciliation and acquire. The existing explicit reconciliation implementation is shared with backup preparation; it accepts only released tombstones with no active or unresolved leases. No cleanup is triggered by status refresh.

During Release, mounted-root metadata belongs to the snapshot filesystem. A group-writable source volume root is not evidence that the protected mountpoint was writable before mounting. Protected ancestors, no-follow checks and the journaled mounted device remain mandatory. Once unmounted, ordinary managed-directory ownership and mode checks apply again. Regression coverage includes source mode 0775, substituted devices, unmounted writable directories, and an acquire reply beyond the status deadline.

Local runtime evidence is private and must not be copied into repository fixtures. A passing fixture does not prove a successful installed backup; release requires current-candidate backup completion and repeat cleanup verification.

Snapshot Access releases a newly acquired lease when its response cannot be delivered to the caller; cleanup failures remain persisted for retry. The regression uses a disconnected Unix socket and verifies cleanup is scheduled only for the undelivered lease.

Access registration reuse checks component and protocol versions in addition to the canonical bundle path. An older component at the same path must enter the existing migration transaction instead of returning ready without updating the manifest.

Snapshot creation may coincide with Time Machine pruning older snapshots. RecordCleanup binds its sole new UUID to the exact name from the fixed tmutil creation receipt, keeps all currently existing non-owned snapshots as the retained baseline, and atomically aligns already-clean same-owner terminal baselines. Missing historical snapshots never become deletion targets. Ambiguous creation receipts or additional new UUIDs remain blocked. Explicit repair may audit inactive pending records together with released drift using the same age- and identity-gated root method; only a released-only residual partition may subsequently be reconciled. Live mounts and unknown or rejected identities remain blocked.

## 快照清理与上传隔离

严格读取产生的加密 direct blob 与 pack 使用现有 filemap 目录下的临时文件暂存，读完并打包后才向原有有界上传队列提交。源完成回调由一次性 RAII guard 保护；daemon 将远端预检移到 acquire 之前，并在回调中启动幂等 lease release。测试在回调中移除模拟快照读取目录，验证直接上传、pack 上传及超时重试继续成功，不再读取源。临时文件在正常返回、错误与 unwind 时清理；强制终止进程可能留下加密临时缓存，不能把它当作持久化恢复格式。

root helper 在既有身份与未挂载检查后，按 journal 精确拥有的 UUID 划分当前 inventory，以 CAS 更新已核验的外部 baseline，再次核验清单后只删除归属快照。外部 Time Machine 快照保留，已有 schema 与状态保持可读。混合 fixture 覆盖 1 条 pending、3 条 released drift、外部快照、重复 release，以及最终 activeMounts=0；原有 foreign UID、重复 UUID、未知 root、并发 inventory 变化等拒绝测试继续适用。

daemon 维护任务与 acquire 共用锁，release 完成通知与 5 秒 tick 触发清理，错误退避上限 60 秒，每轮最多释放 16 条，随后才对 fresh status 中的 released drift 执行 reconciliation。控制操作通过 progress.stage 报告 cleanup_retry/inventory_reconcile，结果包含剩余 pending/drift 数量。Settings 在 mixed pending+drift 状态展示清理动作，只在 pending 为零后展示独立 inventory 动作，并保留 strict mode 阻断。

上述确定性测试不代表已在用户正式实例完成 APFS 快照删除或 Telegram 端到端备份。隔离 macOS 集成与发布后的真实实例验收分别记录，不能用 mocked inventory 冒充真实运行时证据。

标准 helper 安装复用 PendingCleanupUpgrade 分支接受已核验的 pending+released-drift 分区；仅在 Access active_leases=0 时允许保留 pending 并完成替换，持有 mutation lock 后再次核验。卸载与 legacy/unknown 升级的完全 idle 门禁不变。单元测试覆盖有 active reader 时拒绝；hosted fixture 为标准安装构造旧 helper 与 Access pending 记录，验证候选身份及 journal 保留，不声称 fixture 创建了真实快照。
