# Implementation

- Installer startup polling uses a monotonic 20-second window with 250ms sleeps clamped to the remaining time. Immediate connection refusal no longer consumes a fixed four-probe budget, slow calls consume the same clock, and a late ready reply is rejected. Existing component/build and installed-file hash checks remain mandatory. Deterministic clock tests and a hosted mutation of the old four-probe loop cover the regression; the macOS installer fixture can hold a disposable SQLite journal lock to delay the real helper.
- Snapshot failure classification retains the fixed `mount_permission_denied` reason when sanitized diagnostics identify the mount phase and `mount_apfs` permission denial. This distinguishes mounting from generic source access without forwarding paths or arbitrary command output to the UI.

- `crates/snapshot-helper`: user-session Snapshot Access protocol and journal-backed lifecycle,
  including recorded mount-device identities, migratable lease journals, reservation renewal while
  snapshot creation is in flight, unique firmlink resolution, and descriptor-relative no-follow
  reads. Missing or changed mount identities fail the current strict run before source bytes are
  served.
- `crates/snapshot-helper/src/mount_helper.rs` and `src/bin/televybackup-snapshot-mount-helper.rs`:
  root IPC, peer-UID source-path authorization, serialized helper-owned snapshot creation through `RecordCleanup`, UUID journal, crash recovery, and component version `0.5.4` validation that
  binds the requested snapshot name to its manifest UUID before `mount_apfs`, passes the validated
  `/dev/<device>` identity instead of a mutable request pathname, and verifies the mounted device
  afterward. Source-path authorization runs in an exec'd one-shot helper before the server runtime
  starts, and released leases remain as auditable tombstones; a later reserve audits their
  validated baseline and re-blocks the volume if inventory changed. Deletion clears only the
  successfully consumed manifest entries, retains the original reservation baseline, and only
  releases after the post-deletion inventory returns to that baseline; migrated rows without a
  validated baseline remain blocked. A stale row with a mounted root is recoverable only when its
  recorded mount-device identity is present and positive; missing identity remains an unknown
  blocker and ordinary cleanup refuses to unmount the path. The explicit legacy-repair operation
  may backfill that identity only for an age-gated row whose managed root is absent and whose UID,
  volume/device binding, reservation manifest and snapshot inventory all validate, then reuses journal-bound
  `Release`; rows that fail any check remain untouched and blocking. If snapshot deletion succeeds before a process
  crash, an exact reservation-baseline retry records the released tombstone idempotently. The
  installed `0.9.8` helper remains
  migration-readable only.
- `crates/daemon/src/snapshot_client.rs`: restricted IPC client and `BrokeredSnapshotSource`.
- `crates/core/src/backup.rs`: `BackupSource` seam shared by local and brokered reads.
- `crates/cli/src/snapshot_service.rs`: fixed-bundle status plus transactional legacy registration
  migration, owner renewal, and rollback; arbitrary external app installation and DMG-mounted
  production migration are not supported.
- `macos/TelevyBackupApp/SettingsWindow.swift`: per-volume FDA and service state presentation.
- `scripts/macos/build-app.sh`: nested Snapshot Access bundle and the canonical installed-app
  `Program` LaunchAgent plist used by direct `launchctl` registration.
- `scripts/macos/snapshot-access-launchagent-integration-test.sh`: isolated unique-label launchctl
  registration fixture that never starts the Snapshot Access helper.
- `macos/TelevyBackupApp/TelevyBackupApp.swift`: ad-hoc `launchctl` registration, optional
  `SMAppService` registration for signed builds, and migration commit/rollback orchestration.
- `macos/TelevyBackupApp/SnapshotAccessLaunchAgent.swift`: validates the running Access code with Security's dynamic validity check and its canonical bundle path. Direct registration holds a private per-user no-follow advisory lock across all lifecycle commands to serialize application instances, inspects the owned job before bootstrap, retains the current process, and requires a stopped producer plus a verified idle Access status and unchanged PID before restarting stale code. This implements ADR 0016's existing lifecycle boundary; no new architecture decision or helper artifact change is required.
- `crates/cli/src/snapshot_mount_service.rs`: explicit administrator-authorized mount-helper
  LaunchDaemon installation and status contract. Installation acknowledges success only after a bounded IPC probe confirms the current mount-helper component, protocol and candidate source commit, and the installed binary SHA-256 matches the candidate. The v4 wire `helper_version` remains `0.5.0` for the byte-identical approved Access artifact; additive `component_version` identifies the `0.5.4` implementation. Legacy Status without the additive identity fields remains readable but cannot acknowledge a new installation; a known legacy wire version (`0.5.0` or `0.9.8`) may authorize the guarded replacement path even when its positive `active_mounts` aggregate already includes a build identity, provided all additive classification fields are absent and Snapshot Access proves idle. The previous `0.5.3`, `0.5.2` and `0.5.1` components may also authorize that guarded replacement under their existing complete-classification predicates; the current `0.5.4` component may use the same guarded replacement when its build identity is stale and it reports the live, pending, recoverable and unknown partitions but omits only the newer inventory-drift field, or when every pending row has an exact candidate and no live, recoverable or unknown row remains. The candidate helper must classify inherited rows before readiness. The explicit `snapshot.mount_helper.repair_legacy` operation is the only path that may repair a legacy missing-device row; Refresh remains read-only. Unknown versions, current-helper status with a matching build but missing classification, active mounts that have not been safely handed to the candidate, and incomplete candidate partitions remain blocked. An installed helper whose mount state cannot be probed is rejected fail-closed; recovery bootstrap is allowed only when `launchctl` explicitly reports the service absent and the root-owned plist is present. Installer and helper mutating IPC share a root-owned file lock through the busy check, asset replacement and old-service bootout; recovery bootstrap releases and reacquires that lock before the final busy check, and replacement releases it before bootstrap so the new helper can acquire it during startup recovery.
- The current helper component is `0.5.4`; the compatibility text above describes the same guarded replacement predicates for the previous `0.5.3`, `0.5.2` and `0.5.1` components.
- Snapshot Access persists a `cleanup_pending` lease when root-helper release is unavailable, retries that durable cleanup in the background and during status probes, and accepts an idempotent release retry for the recorded lease. The CLI and daemon expose an explicit cleanup-retry operation that first proves Snapshot Access is idle, verifies the complete pending-only classification, and then reuses the journal-bound `Release` path; an inventory mismatch remains `snapshot_mount_helper.pending_cleanup` and fail-closed. The daemon also retries transient release transport failures, so a helper restart does not strand an active mount row until the next process restart.
- `macos/TelevyBackupApp/SnapshotMountHelperInstallation.swift`: coordinates administrator installation, renewed user-level Access registration, and the subsequent Access status check; preserves installation and registration errors across refresh, and rejects an exit-zero installation whose communication check still fails.
- `crates/daemon/src/control_ipc.rs` queries root Status independently of the approved Access artifact and exposes reachability, candidate readiness and build identities separately. `SnapshotMountHelperReadiness.swift` also binds readiness to the current app bundle, conservatively accepts legacy JSON as update-required, and supplies the production Settings update action. Final installation confirmation uses this same predicate. Status refresh remains read-only; cleanup retry is a separate serialized IPC operation.
- Root Status classifies live, pending-cleanup, recoverable-stale, inventory-drift, and unknown journal rows with additive optional fields. Missing additive fields remain unknown rather than zero for status, readiness, and reconciliation; known active and mixed test fixtures explicitly set every known category to zero when absent so they do not accidentally exercise the legacy-unknown path. The daemon exposes serialized `snapshot.mount_helper.reconcile`, `snapshot.mount_helper.retry_cleanup`, `snapshot.mount_helper.reconcile_inventory`, and `snapshot.mount_helper.repair_legacy` operations. Stale reconciliation requires the current helper component and build identity; cleanup retry accepts only the current or immediately previous cleanup-capable component, with the v4 wire identity and complete pending-only classification still required; inventory reconciliation accepts only exact released tombstones whose device/volume identity and changed baseline are verified. Legacy repair checks Snapshot Access idle, verifies the complete additive partition, and delegates age-gated candidate validation and journal-bound Release to the root helper. Each mutating operation queries the authenticated UID's complete helper Status, applies the same validation helper before and after releasing, and returns counts only. Ordinary Snapshot Access release never re-baselines a released row, and unknown states or malformed released tombstones remain untouched and reservation-blocking. Reconciliation writes the new inventory baseline and its confirmation in one SQLite transaction, so a failed post-update inventory check rolls the row back and leaves the drift blocker intact. Status requests serialize behind the helper's bounded status lock, and volume-inventory commands have a bounded child-process timeout. The Unix CLI delegates cleanup retry, inventory reconciliation and legacy repair to daemon operations so they share the maintenance lock with backup acquisition; the legacy previous helper remains eligible for a guarded update when it reports pending-only status without the newer optional inventory-drift field. Pending-cleanup, live, unknown, legacy, inconsistent, or identity-mismatched rows keep stale reconciliation blocked; inventory drift keeps cleanup retry blocked; inventory reconciliation and legacy repair never open source files. Settings exposes each action only for its verified classification, waits for the operation's terminal state with a bounded polling deadline before refreshing, while an unreachable helper retains an install action.
- `SnapshotMountHelperStatusView.swift` is shared by Settings and the GitHub-hosted synthetic renderer. Hosted tests cover a reachable same-version old helper, missing/malformed identity, a stale daemon ready flag, a verified replacement and post-install rejection. The view distinguishes live, pending-cleanup, recoverable-stale, inventory-drift, and unknown rows, exposes each action only for its verified candidates, and exposes cleanup retry for a verified pending-only inventory from either the current or immediately previous cleanup-capable helper. The previous helper is deliberately allowed to clear only the journal-bound pending rows; it still cannot be treated as current or update-ready. `test-helper-readiness-regression.sh` proves the tests reject the old connectivity-only rule by changing a private copy of the production predicate, displaying the exact mutation, and checking the specific failure before running the unchanged candidate. This is a deterministic readiness regression, not a full backup acceptance.
- Timed-out root-helper commands run in a private process group. The helper terminates that group and drains nonblocking stdout/stderr pipes without unbounded reader-thread joins, so a descendant cannot keep the mutation lock held after the command deadline.
- `scripts/macos/snapshot-helper-upgrade-integration-test.py`: dispatch-only GitHub-hosted regression retains a real rc.114 Access LaunchAgent through an in-place rc.120 artifact replacement, reproduces the protocol mismatch, and exercises candidate production registration and installation coordination to restore communication. It validates actual dynamic identity, healthy-process retention, and service cleanup with empty synthetic configuration. Initial service checks require confirmed absence and reject inspection errors. Path-absence checks include dangling symlinks. Cleanup confirms both services are absent before deleting fixture-owned targets and preserves the targets if shutdown cannot be verified; it does not claim APFS/FDA acceptance.
- `scripts/macos/mount-helper-install-integration-test.py`: dispatch-only GitHub-hosted macOS regression using real published helper binaries and a synthetic historical service, empty configuration, and isolated journals. It reproduces the protocol error before installation, accepts both the published legacy status and the intermediate build-identity-only status, and checks the candidate component identity after replacement without snapshots or TCC changes. The PR workflow invokes the recovery fixture through a block scalar so its `--helper` argument is preserved.
- `scripts/macos/test-snapshot-mount-recovery.py`: dispatch-only GitHub-hosted macOS regression using a disposable APFS image and isolated root-helper, daemon, Access, and journal state. The fixture proves classification, inventory reconciliation, and CLI/daemon legacy-repair fencing. It deliberately does not create snapshots: the hosted runner rejects `tmutil localsnapshot` for the disposable image and `diskutil apfs` has no create operation. A structurally valid but unobservable legacy manifest must remain an unknown blocker, so the fixture cannot claim a release or deletion that was not proven; repair failures use the dedicated `snapshot_mount_helper.repair_required` code. Successful journal-bound release semantics remain covered by deterministic helper tests.
- `crates/snapshot-helper/src/mount_helper.rs`: source volume queries use the kernel device from a pinned no-follow directory metadata descriptor. The non-root authorization child must open the same device/inode, and reservation rechecks the source identity after authorization and inventory collection. System command errors carry fixed stage/category, exit status, channel and an allowlisted diagnostic summary; arbitrary stdout/stderr and plist parser details are never echoed.
- `scripts/macos/test-snapshot-source-reservation.py` and the default-off `snapshot_source_validation` dispatch input in `CI (main)`: hosted macOS creates a disposable APFS image, reproduces the baseline nested-directory `diskutil` exit 1 twice through production Reserve, then checks candidate Reserve, an explicitly empty inventory and security negatives. The same lane tests helper/CLI/daemon/core contracts and candidate installation with byte-identical approved Access. No `tmutil`, snapshots, FDA changes, owner data or local application execution is involved. Full backup completion remains a separate post-release observation.
